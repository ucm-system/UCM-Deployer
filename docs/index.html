UCM Deployer

面向 vLLM / vLLM-Ascend / SGLang 运行环境的 Windows 桌面工具。专注 UCM 安装、环境检测与推理服务拉起：服务器管理（环境检测）、UCM镜像准备、UCM容器环境准备、容器内复检、推理服务拉起与运维清理。

当前版本 v0.6.1 · 支持 Ascend NPU · NVIDIA GPU · Linux 服务器 · Docker

工具简介

UCM Deployer 是 Unified Cache Management（UCM）的安装、环境检测与推理服务拉起工具。它把原本需要手工执行的 SSH 命令、镜像导入、离线 whl 安装、docker run 参数拼装、UCM 配置文件写入和容器内环境检查，收敛为五个向导步骤（另提供面向多台服务器场景的可选批量部署）；步骤 3 完成容器创建与 UCM 文件配置，步骤 5 提供拉起命令指引与连通性自动验证。

① 服务器管理SSH 登录与环境检测（设备 / CANN / 内存 / Docker）
② UCM镜像准备复用或构建含 UCM 的镜像
③ UCM容器环境准备创建或复用 UCM 推理容器
④ UCM容器环境预检驱动 / 内核 / 带宽 / SMMU 检查
⑤ 推理服务拉起拉起命令指引与连通性自动测引
可选批量部署（多台服务器）

凭据复用

密码或私钥登录，密码 Fernet 加密保存在本机，下次打开自动复用。

设备感知

自动识别 Ascend / NVIDIA 型号、卡数与 CPU 架构，并按宿主机实际资源生成容器参数。

镜像准备

单一来源选择器：复用服务器镜像、离线导入 tar 包，或由目标服务器直连仓库拉取；本地无需 Docker Desktop。

按需构建

仅在基础镜像未安装 UCM 时上传 wrapt、UCM、ucm-toolkit whl 并构建新镜像。

命令透明

所有 Docker 命令先完整展示，允许编辑，再执行，避免黑盒操作。

UCM容器环境预检

显式选择容器，检查驱动、内核、共享内存、AIO、存储带宽与 SMMU；UCM 与驱动版本支持多来源补齐。

推理服务拉起

拉起命令模板（环境变量 + --kv-transfer-config 接入）与连通性自动测、拉起命令模板（环境变量 + --kv-transfer-config 接入）与连通性验证 curl，一键复制照做即可。

运维善后

按关键字筛选并清理容器或镜像，删除前展示完整对象列表。

快速开始

方式一：直接使用 EXE（推荐）

直接下载最新版 UCM-Deployer.exe，双击即可运行，无需安装 Python。

.\\UCM-Deployer.exe --smoke

方式二：从源码运行

git clone https://github.com/ucm-system/UCM-Deployer.git
cd UCM-Deployer
python -m venv .venv
.venv\\Scripts\\pip install -r requirements-dev.txt
.venv\\Scripts\\python -m pytest
.venv\\Scripts\\python main.py

方式三：本地打包 EXE

powershell -ExecutionPolicy Bypass -File scripts\\build_exe.ps1
目标服务器要求 Linux + SSH + Docker；Ascend 服务器需宿主机可用 npu-smi；NVIDIA 服务器需 nvidia-smi 与 nvidia-container-runtime。 使用镜像仓库拉取时，目标服务器需能访问对应仓库；本地无需 Docker Desktop。

步骤 1

服务器管理

登录要操作的服务器并执行环境检测（设备 + 宿主机）。一次只登录一台服务器，后续所有操作都作用于当前勾选的服务器；多台服务器可用「🧪 批量测试连接」与「🔍 批量环境检测」并行处理，每台独立日志页签。

操作流程

  1. 点击「➕ 添加服务器」，填写名称、地址、账号、认证方式与备注。
  2. 点击「🔌 测试连接」确认 SSH 可达。
  3. 点击「🔍 环境检测」，自动识别设备类型、型号、卡数与 CPU 架构，并同步预检宿主机环境（加速器驱动 / 内核版本 / SMMU，与步骤 4 同一套判定口径，提前暴露基础环境问题）。
  4. 勾选「登录」，选择本次操作目标。
探测项来源用途
设备类型与型号npu-smi info / nvidia-smi匹配基础镜像平台，生成设备映射
卡数设备探测结果辅助校验步骤 3 探测到的 davinci 节点数量
CPU 架构uname -m校验 whl 架构，并为镜像仓库拉取选择 linux/amd64 或 linux/arm64
加速器驱动version.info / npu-smi / nvidia-smiAscend HDK 须高于 25.2.0；与容器内预检同一套解析口径
内核版本uname -r须 ≥ 5.10（按 major.minor 比较）
SMMU（宿主机）dmesg不应出现 arm-smmu-v3；已开启建议进 BIOS 关闭
环境检测结果 驱动 / 内核 / SMMU 检查结果逐项写入任务日志（PASS / WARN / FAIL / SKIP）；存在 FAIL 项会弹窗提示——建议先修复环境，再准备镜像与创建容器。
注意 若探测不到设备，请确认宿主机已安装 npu-smi 或 nvidia-smi，且命令在 PATH 中可用。
步骤 2

UCM镜像准备

优先复用已安装 UCM 的镜像；仅在确需制作新镜像时，才把 wrapt、UCM 与可选的 ucm-toolkit 安装进基础镜像。

操作流程

  1. 选择镜像来源：默认复用「服务器已有镜像」，无需填写仓库地址；离线场景选择 tar / tar.gz 导入（「服务器保存路径」默认 /tmp，大镜像包建议改为大容量目录如 /data，避免空间不足）；在线场景输入仓库地址。
  2. 服务器直连拉取：目标服务器按 CPU 架构生成可编辑的 docker pull --platform 命令，本地无需 Docker Desktop，也不生成或上传 tar.gz。
  3. 检查 UCM：点击「✅ 检查所选镜像 UCM」。已安装则记录该镜像并直接进入步骤 3，无需构建。
  4. 按需构建：仅在基础镜像未安装 UCM 时选择 wrapt、UCM 与 ucm-toolkit whl。
  5. 确认新镜像名：默认生成 <基础镜像名>:ucm-<UCM版本>，也可手动修改。
  6. 点击「🔍 校验匹配」，确认设备平台与 whl 架构匹配。
  7. 点击「🔨 开始构建」，上传安装包并执行 docker build。
校验项规则失败处理
设备平台NPU 对应 ascend 镜像，GPU 对应 nvidia / CUDA 镜像拒绝构建并提示更换镜像
whl 架构文件名中的 x86_64 / aarch64 需与服务器 CPU 架构一致拒绝构建并标出不匹配包
UCM 安装结果构建完成后在镜像内执行包检测构建失败并展示完整日志
服务器拉取前置条件 使用镜像仓库模式时，目标服务器需已安装 Docker 并能访问仓库。工具会按目标服务器 aarch64 / x86_64 选择对应平台，避免拉取错误架构镜像。
步骤 3

UCM容器环境准备

可基于 UCM 镜像创建新容器；如果服务器上已有安装 UCM 的容器，可跳过创建，直接进入步骤 4 选择该容器预检。创建前自动检测同名容器：已存在同名容器时明确提示（不会执行到 docker run 才因容器名冲突失败），可通过「工具 → 清理指定容器」删除后再创建。

选择镜像

进入页面后自动加载镜像列表。选择镜像时会后台校验 UCM 是否安装：已安装则显示版本；未安装则提示回步骤 2 构建或更换镜像。

复用已有容器 若目标容器已安装 UCM，无需重复创建。直接进入步骤 4，刷新容器列表并选择该容器即可开始环境复检。

容器参数

进入页面后自动探测实际存在的 Ascend 设备节点与系统挂载。兼容 Ascend950PR / A5：缺失 /dev/devmm_svm 时不生成该参数，存在 /dev/ummu 或 /dev/uburma 时自动添加 --privileged=true。

参数默认值说明
容器名ucm-vllm同名容器已存在时会提示处理
共享内存--shm-size 512g满足 UCM KV-cache 页缓存要求
网络NPU：--net=host
GPU：-p 8000:8000		按设备平台自动生成

挂载配置（统一挂载表）

KV Cache / 模型 / 自定义挂载统一在同一张表格中维护（类型、宿主机路径、容器内路径、只读四列），共用一套「➕ 添加」入口与右键菜单（🗑 移除选中 / 🔎 批量校验）；「🌐 新增远端挂载」支持在宿主机上挂载 NFS over RDMA / DTFS 远端文件系统（命令实时预览，挂载成功后自动加入映射表）；默认表为空（即不挂载任何目录），需要时选择类型、填写路径后添加；选中行可校验挂载点是否位于同一文件系统（KV Cache 要求）。

  • KV Cache 行：容器内路径自动与宿主机相同（锁定不可编辑），支持容器内 / 宿主机目录浏览，并可检查文件系统类型。
  • 模型行：挂载到容器内 /models，默认只读，最多一行。
  • 自定义行：任意宿主机与容器路径映射，可选择只读。

命令示例

# Ascend NPU：仅映射实际存在的设备节点与系统资源
docker run -itd \\
  --name ucm-vllm \\
  --entrypoint /bin/bash \\
  --net=host --shm-size 512g \\
  --device /dev/davinci0 --device /dev/davinci1 \\
  --device /dev/davinci_manager --device /dev/hisi_hdc \\
  --device /dev/ummu --device /dev/uburma \\
  --privileged=true \\
  -v /usr/local/Ascend/driver:/usr/local/Ascend/driver \\
  -v /etc/ascend_install.info:/etc/ascend_install.info \\
  -v /etc/hccl_rootinfo.json:/etc/hccl_rootinfo.json \\
  -v /etc/hixlep:/etc/hixlep \\
  -v /usr/local/dcmi:/usr/local/dcmi \\
  -v /usr/local/sbin:/usr/local/sbin \\
  -v /usr/local/bin/npu-smi:/usr/local/bin/npu-smi \\
  -v /mnt/kvcache:/mnt/kvcache \\
  -v /data/models/Qwen3-32B:/models:ro \\
  vllm-ascend-ucm:v0.26.0rc1

# NVIDIA GPU：使用 nvidia-container-runtime
docker run -itd \\
  --name ucm-vllm \\
  --entrypoint /bin/bash \\
  --runtime nvidia --gpus all \\
  -p 8000:8000 --ipc=host --shm-size 512g \\
  -v /mnt/kvcache:/mnt/kvcache \\
  -v /data/models:/models:ro \\
  vllm-openai-ucm:latest
先编辑，再执行 生成的命令完整展示在编辑框中。命令固定使用 --entrypoint /bin/bash，只创建并保持 Bash 容器运行，不启动 vLLM。你可以按环境需要修改参数，点击「🚀 创建容器」后按编辑框内容执行。
步骤 4

UCM容器环境预检

显式选择目标容器，并在该容器内运行 ucm-toolkit run precheck，复检容器内环境，提前发现可能影响 UCM 启动或缓存读写的问题（宿主机侧的驱动/内核/SMMU/CANN/内存/Docker 检测在步骤1 环境检测完成）。若镜像内未安装 ucm-toolkit 或预检未产出任何检查项，预检会明确报错并给出排查指引（如回步骤 2 重装 UCM 组件 / 重建镜像），不会把失败伪装成全部通过。

选择目标容器

  1. 进入步骤 4 后点击「🔄 刷新容器」，工具执行 docker ps -a 获取服务器上的容器。
  2. 在「目标容器」下拉框中选择要预检的容器；也可输入容器名。
  3. 确认状态行显示 目标容器：... 后，再开始预检。
支持已有容器 服务器上已经创建且安装 UCM 的容器无需重建；刷新并选择该容器后，可直接执行环境复检。

检查模式

模式行为适用场景
环境检查 + 带宽测试在指定挂载目录创建临时子目录，执行读写负载后自动清理验证 KV Cache 存储路径实际吞吐
仅环境检查追加 --skip-bandwidth，检查驱动、内核、共享内存与 AIO快速排查基础环境

步骤 5

推理服务拉起

拉起命令指引 + 自动验证：UCM 配置文件的编辑与写入已在步骤 3「UCM 文件配置」模块完成（批量部署由右上角「创建容器并配置UCM文件」开关一并执行）；本页给出容器内执行的拉起命令模板（需修改片段黄底高亮，UCM_CONFIG_FILE 与步骤 3 写入路径联动），验证命令按输入的服务器 IP、端口与模型名自动生成——可复制到宿主机另开的终端手工执行，也可点击「⚡ 执行连通性测试」由工具通过 SSH 自动执行并逐项判定。

① 推理服务拉起命令（在容器内执行）

注意事项：

  1. 拉起服务前需先导出环境变量：export ENABLE_UCM_PATCH=1、export VLLM_CPU_AFFINITY=1；
  2. 拉起命令后必须附加 --kv-transfer-config，通过 UCMConnector 使 vLLM 接入 UCM；
  3. 其中 UCM_CONFIG_FILE 为 UCM 配置文件路径，指向步骤 3「UCM 文件配置」写入容器内的 yaml（可自定义修改，两处路径必须一致）；
  4. PD 分离部署时，--kv-transfer-config 只需在 Prefill 实例的拉起命令中添加，Decode 实例无需添加。

② 验证连通性（服务就绪后，在宿主机另开终端）

在页面输入框填写服务服务器 IP（留空即 127.0.0.1，从其他机器执行时填目标 IP）、端口（默认 7800）与模型名（默认 qwen3.8，须与 vllm serve 的模型一致），下方验证命令自动生成；点击「⚡ 执行连通性测试」由工具通过 SSH 在目标服务器上自动执行三项检查并逐项判定（PASS/FAIL 结果写入任务日志）：服务健康检查 /health、模型列表 /v1/models、对话验证 /v1/chat/completions（完整 JSON 载荷、关闭思维链、校验回复内容），失败时给出排查提示。

唯一执行入口 连通性测试通过任务面板在后台执行（单服务器）；写入 UCM 配置文件的操作已前移到步骤 3 / 批量部署，避免两处重复填写。
步骤 4 之后

（可选）批量部署

面向多台服务器场景：在一台源服务器制作好镜像后，向多台目标并行执行「镜像分发 → 创建容器并配置UCM文件 → 环境预检」。单台服务器场景请直接使用步骤 3 / 4 / 5，无需本功能。

  • 镜像分发三方式：镜像包中转（源服务器 docker save -o 导出 → 本机中转 → 各目标 docker load）、镜像仓库拉取（各目标从仓库拉取）、服务器直传（源服务器 docker save -o 导出 → 各目标经服务器间 scp 拉取 → docker load，镜像不经本机、不占本机磁盘与带宽）；tar / 直传模式下源服务器先导出镜像包，目标保存路径可配置（默认 /tmp，大镜像包可指定如 /data），docker load 校验完成后自动清理临时包，全部结束后源端镜像包自动清理；直传的密码认证优先 sshpass，目标未安装时自动改用 OpenSSH 自带的 SSH_ASKPASS 机制代输（免安装，临时脚本 700 权限、传输后立即删除；OpenSSH >= 8.4 无需额外依赖）。
  • 布局自上而下：镜像来源 → 目标服务器 → 部署配置模板 → 批量执行，与步骤 1-4 阅读顺序一致；上半（目标服务器 + 配置）与下半（批量执行 + 任务面板）可拖分栏，任务运行时进度表与日志可按需扩高。
  • 目标服务器来自步骤 1：列表与「服务器管理」完全一致；**点击行任意位置即可勾选**（勾选行整行高亮），点「部署」列表头=全选/清空，右键菜单提供全选/清空/刷新列表；注册表为空时表格显示引导；新增 「环境」列展示步骤 1 宿主机环境检测汇总（PASS / WARN / FAIL / 未检测，悬浮查看驱动、内核、SMMU 各项明细）。
  • 部署配置四页签：镜像与分发（镜像来源 + 分发方式 + 目标保存路径）/ 容器配置（含「同名容器先删除再创建」、自定义 docker run 命令）/UCM文件配置（可编辑配置模板 + 容器内路径，是否写入由右上角「创建容器并配置UCM文件」开关决定——创建容器即写入）/预检配置，挂载配置同样使用统一挂载表，设备差异逐台自动适配；页签栏右上角为三个执行阶段开关（分发镜像 / 创建容器并配置UCM文件 / 环境预检），取消勾选则跳过该阶段（「创建容器并配置UCM文件」未勾选时「容器配置」与「UCM文件配置」两页签均不可选中；预检配置页签置灰；镜像与分发页签保持可编辑——仅禁用分发参数区，镜像名始终可填写，不分发时镜像须已存在于各目标服务器）；预检 JSON 编辑框预填常用配置模板（内核版本 / 带宽参数，叠加于 ucm-toolkit 出厂默认之上，只需写要覆盖的键），未勾选自定义时编辑框置灰仅作参考；支持勾选「自定义 docker run 命令」（同构集群整条执行，{image} 占位符自动替换镜像，可一键生成样例；与附加参数互斥置灰）；分发前总是自动检测目标已有同名镜像并跳过（重复执行安全）。
  • 独立进度与日志：每台服务器一行进度条（分发 45% / 创建 25% / 预检 30% 权重）与独立日志页签，单台失败不影响其余；部署可随时取消（远端长任务同步中断）；容器创建后自动确认运行状态（启动即退出时立即诊断并提示 docker logs 定位）；结束后汇总弹窗简短标注每台结果，完整失败原因见各服务器日志页签；挂载表右键菜单提供「🗑 移除选中 / 🔎 批量校验」——批量校验对全部勾选目标并行检查每个宿主机路径是否存在（test -d），结果与 mkdir -p 建议写入各服务器日志页签；「🌐 批量新增远端挂载」在全部勾选目标的宿主机上挂载远端文件系统（NFS over RDMA：mount -t nfs -o vers=3,nolock,proto=rdma,nconnect=8；DTFS：mount -t dtfs -o rw,eventual,cid=<CID>,dn=dns_local，命令实时预览，挂载前自动 mkdir -p 本地目录、成功后 mountpoint -q 校验并把目录加入映射表）；支持整套部署模板（JSON）导出 / 导入：服务器登录信息（自动写入服务器管理并勾选为目标）+ 镜像与分发 + 容器/预检配置 + 执行阶段开关，一次配置他机复用。

预检参数配置

预检参数来自 ucm-toolkit 的 JSON 配置。步骤 4 的「⚙ 预检参数配置...」提供容器内查看、编辑、保存与恢复默认能力。

配置位置说明
出厂默认<site-packages>/ucm_toolkit/tools/precheck/precheck.defaults.json随 ucm-toolkit whl 安装
自定义配置容器内 /root/ucm-deploy/precheck.json本工具保存，预检自动引用

自定义配置叠加在出厂默认之上，只需写要覆盖的键。例如仅调整带宽阈值：

{
  "bandwidth": {
    "threshold_gb": 4.0
  }
}

默认带宽矩阵

2 档分片（180 KiB / 8 MiB）× 3 档并发（1 / 8 / 16）× 2 个引擎（psync / aio），共 12 个组合；每个组合执行 dump、load、mixed 三阶段。

常见问题

密码安全吗？

密码使用 Fernet 对称加密保存在本地 ~/.ucm_deployer/servers.json，密钥保存在同目录 .secret.key。密文被单独拷贝时无法直接还原明文。

按需构建镜像时 wrapt 安装失败怎么办？

确认 wrapt whl 的架构标记与服务器 CPU 架构一致：x86_64 服务器选择 manylinux x86_64 包，aarch64 服务器选择 manylinux aarch64 包。

构建成功但提示未检测到 UCM？

UCM 包名存在平台变体，例如 uc-manager-cann910-a2。工具按 uc-manager* 前缀检测；若仍失败，可手动执行 docker run --rm <镜像> pip list | grep uc 验证。

提示镜像平台与设备不匹配？

按镜像名推断的平台与服务器设备类型不一致。请更换匹配的基础镜像；自定义镜像名无法识别平台时会降级为警告。

容器内 npu-smi 报 rc=172 / -8020？

通常表示 NPU 正被其他进程或容器占用，宿主机 npu-smi info 仍可查看。该警告不影响带宽检查，停用占用方后重试。

带宽测试某组合超时？

常见于 aio 引擎、高并发与慢存储组合。可通过预检参数配置调低 combo_timeout、减少 worker 数或提高 fs.aio-max-nr。

日志在哪里？

本地日志位于 ~/.ucm_deployer/logs/ucm_deployer.log，也可通过菜单「帮助 → 打开日志目录」打开。
